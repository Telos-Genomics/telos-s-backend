# Telos-S Evaluation Track (Fase A)

This directory holds the prospective-validation infrastructure for Telos-S:
the machinery that turns "retrospectively consistent" (paper §5) into a
prospectively testable claim — or discovers it does not hold, which is
also a publishable result and the decision gate for everything downstream.

No file here changes pipeline behavior. The evaluation track only reads
pipeline outputs and records predictions, outcomes, and comparisons with
server-generated timestamps and configuration hashes.

## How it plugs into the existing pipeline

```
 ingest FASTA → spike_extractor → sequence_aligner → [impute] → oracle → comparator
                                                                              │
                                                                              ▼
 retired numbers live here ──►  report_spike_*.csv ──┬──► import-report ──► per_mutation_cache.csv
                               mutation_predictions_*.json                          │
                                                                                  ▼
 prospective isolate ──► register ──► prospective_registry.jsonl    evaluate / search (calibration)
                                                                              │
 retrospective curation ──► retrospective_set.csv ───┬──► import-telos ──► method_scores.csv ──► table / compare
                                                     └──► external runs ──►─┘        (benchmark)
```

Concretely:

| Pipeline output | Eval entry point | Stored in |
|---|---|---|
| `report_spike_*.csv` (mutations, LLR, Reliability) | `eval_calibrate.py import-report` | `per_mutation_cache.csv` |
| Full analysis of a new isolate (score, Qr, Prophet) | `eval_harness.py register` | `prospective_registry.jsonl` (created on first use) |
| Curated isolate + observed trajectory | manual row + `eval_retrospective.py validate` | `retrospective_set.csv` |
| Current-config scores of cached isolates | `eval_benchmark.py import-telos` | `method_scores.csv` (created on first use) |
| CoVFit / EVEscape runs from their own pipelines | `eval_benchmark.py import-scores` | `method_scores.csv` |

## Workflow 1 — Prospective registration (the core discipline)

For every newly released isolate, in this order:

```bash
python3 modules/eval_harness.py freeze                                  # note the config hash
# ... run the normal backend analysis, get job_id ...
python3 modules/eval_harness.py register --json '{
  "accession": "PZ155177.1", "job_id": "job_abc123",
  "aggression_score": 2280.5, "sequence_quality_Qr": 100.0,
  "reliable_mutations_n": 69, "lineage": "Omicron KP.3.1.1",
  "prophet": [{"wuhan_position": 681, "top_aa": "S",
               "pst_pct": 22.4, "alert": true}]
}'
```

Rules: the timestamp, config snapshot hash, code SHA and model id are
generated by the harness — caller-supplied values are overwritten.
Register BEFORE looking at the isolate's epidemiological trajectory.
Annotate outcomes afterwards, in a separate step. A retrospective
accession must never enter this registry (`eval_retrospective.py
summary --registry` enforces it and fails on leakage).

## Workflow 2 — Growing the retrospective set

Target: 20–40 isolates with independently documented trajectories
(n=4 cannot fit anything). Append rows to `retrospective_set.csv`,
then:

```bash
python3 modules/eval_retrospective.py validate   # acceptance rules
python3 modules/eval_retrospective.py summary    # counts + leakage check
```

Acceptance rules (enforced, see `modules/eval_retrospective.py`):
human clinical isolate with GenBank accession; `dictionary_coverage`
yes/no; `outcome_tier` in baseline/elevated/critical/pending describing
the OBSERVED trajectory, never the Score; any non-pending tier needs
external evidence cited (WHO report, literature) — scores cannot
justify their own outcome; exclusions need a written reason;
`pending` is the only honest value for freshly released isolates.

## Workflow 3 — Mutation cache (recompute without GPUs)

`𝒜 = Σ|c₁·ω + c₂·ζ|` over Trusted mutations (§2.4.1), so every
parameter combination rescores exactly from cached (zone, LLR) rows —
a full grid costs milliseconds instead of GPU hours. The cache is built
only from real pipeline reports, never by hand:

```bash
python3 modules/eval_calibrate.py init-cache
python3 modules/eval_calibrate.py import-report --report output/s/reports/report_spike_X.csv --accession XXXXXX.1
```

## Workflow 4 — Calibration (honest fitting)

```bash
python3 modules/eval_calibrate.py evaluate   # scores vs tiers + Spearman under CURRENT config
python3 modules/eval_calibrate.py search     # grid search — REFUSES below 4 annotated isolates / 2 tiers
python3 modules/eval_calibrate.py tau-scan   # placeholder: reports itself pending (needs a prophet cache)
```

Constraints: zone weights must preserve RBM ≥ RBD ≥ Furin ≥ Other
(§2.4.2), `w_other` anchored at 1.0; rank-based objective (Spearman),
never magnitude fitting; leave-one-out reports parameter STABILITY,
not precision. τ stays heuristic (§2.5.2, §4.4): threshold ROC would
need position-level truth labels, which do not exist.

## Workflow 5 — Benchmark (symmetric comparison)

Same isolates, same outcomes, same metric (Spearman) for Telos,
CoVFit and EVEscape (§4.1 for what each method is):

```bash
python3 modules/eval_benchmark.py init-scores
python3 modules/eval_benchmark.py import-telos                              # pins current config hash
python3 modules/eval_benchmark.py import-scores --csv ext_runs.csv          # accession,method,score,model_version
python3 modules/eval_benchmark.py table                                     # per-isolate listing, always allowed
python3 modules/eval_benchmark.py compare                                   # statistics, guardrailed like search
```

Scores are monotone-increasing in risk by convention; transform
inverted methods before import and say so in notes. This repo runs no
external model — CoVFit/EVEscape scores come from their own pipelines
and enter here with `model_version` cited.

## Decision gate

When `search` and `compare` stop refusing (≥4 annotated outcomes, ≥2
tiers, growing toward dozens): if the prospective signal holds,
calibrated constants + benchmark become the follow-up publication and
the sales argument for labs/reinsurers. If it does not hold, the
honest pivot is "QC + lineage + reporting tool" — the registry is the
receipt either way.

## Files

| File | Role |
|---|---|
| `registry_schema.json` | Contract v1 of a prospective registry entry |
| `retrospective_set.csv` | Curated isolates + observed outcomes (seed: 4 paper isolates) |
| `per_mutation_cache.csv` | Cached (zone, LLR) rows (created via `import-report`; absent until then) |
| `prospective_registry.jsonl` | Sealed predictions (created on first `register`; never hand-edit) |
| `method_scores.csv` | Benchmark scores with provenance (created via imports; absent until then) |
